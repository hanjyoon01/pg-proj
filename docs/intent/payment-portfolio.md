# 결제 처리 포트폴리오 — 확정된 의도 (Statement of Intent)

확정일: 2026-11-22 (interview-me, 사용자 명시적 yes)
개정: 서비스 주제 선정·배포 제외, 모의 PG 채택 반영 (사용자 명시적 yes)
개정 2 (2026-11-22): spec 작성 중 이체를 후순위로 결정 (사용자 선택: "결제와 원장만, 이체는 후순위"). 원장은 복식부기·불변 분개로 한다. 상세는 `docs/spec/03-payment-server.md`

## 목표 (Why)

- 금융권 취업용 포트폴리오로 결제 처리 시스템을 만든다. "결제 도메인을 이해하고, 깨지지 않게 만들 수 있다"는 점을 증명하는 것이 목적이다.
- 가장 깊게 다룰 영역: (a) 승인·취소·환불 같은 실시간 거래 흐름, (b) 원장 기록(복식부기, 불변 분개). 멱등성, 트랜잭션 정합성, 실패 복구를 보여준다. 이체는 후순위이며, 일정이 남으면 실제 돈 이동 없이 내부 장부 이동만 추가한다.
- 특정 서비스 도메인(숙박 등)은 얹지 않고, 순수 결제 처리 모듈을 로컬에서 구현한다.
- 외부 PG는 토스페이먼츠·포트원 같은 실제 PG의 API 규격(승인·취소·웹훅·상태 전이)을 참고한 모의 PG를 직접 만들어 사용한다. 모의 PG는 어댑터 인터페이스 뒤에 두어, 나중에 실제 PG 샌드박스 어댑터로 교체할 수 있는 구조로 설계한다.
- 모의 PG에서는 타임아웃, 응답 유실, 중복 콜백 같은 실패 상황을 의도적으로 재현할 수 있어야 한다.

## 대상 (Who)

- 1차: 채용 담당자·면접관 (은행, 카드사, 금융결제원 등 금융 인프라 기관의 백엔드 직무)
- 서비스 실사용자: 없음.

## 완료 기준 (Success)

- GitHub에 코드 공개
- 동시성·중복 요청·중간 실패 시나리오의 테스트 결과
- 동시 결제 상황은 부하 테스트로 직접 재현
- 면접에서 로컬 환경으로 시연 가능

## 제약 (Constraint)

- Java Spring Boot, PostgreSQL (Redis는 필요해질 때 추가)
- 기간: 약 1개월 (설계 → 구현 → 테스트)
- 개인 작업, 로컬 실행 기준
- 외부 PG: 규격을 모방한 모의 PG + 교체 가능한 어댑터

## 하지 않을 것 (Out of scope)

- 서비스 주제 선정, 특정 도메인(숙박 등) 연동
- 서버 배포 (로컬 시연만)
- 실제 PG 샌드박스 연동 (후순위, 어댑터 교체로 추후 가능)
- 대사·정산(c)은 후순위
- 이체는 후순위 (계좌 간 이체 API는 만들지 않는다. 일정이 남을 때만 내부 장부 이동을 검토)
- WMS 서비스 연동 안 함
- 대형 플랫폼(콘서트 예매 등) 직접 상용화 안 함
- 돈을 직접 보관·이체하는 전자금융업 수준의 기능 안 함 (규제 요건은 진행 전 별도 확인 필요)
