# Spec 03 — 우리 결제 서버 설계

상태: 초안 (2026-11-22). 확정 항목과 제안 항목을 구분해서 표시합니다.
근거: `docs/intent/payment-portfolio.md`, `01-pg-reference.md`, `02-toss-api-contract.md`

## 1. 확정된 결정 (사용자 확인)

| 항목 | 결정 |
|---|---|
| 결제 진입 방식 | **결제 생성 → 승인 2단계.** `READY`에서 결제를 생성하고, 인증 후 승인을 요청한다. 토스 흐름과 같다 |
| 원장 모델 | **복식부기 + 불변 분개.** 모든 거래를 차변·대변 분개로 기록하고 수정·삭제 없이 추가만 한다. 정정은 역분개로 한다 |
| 자체 멱등키 | **받는다.** 우리 서버도 클라이언트(가상의 상점 서버)의 `Idempotency-Key`를 받아 처리한다. 모의 PG와 같은 DB 방식(`02`의 5절, 7-0절)을 재사용한다 |
| 이체 범위 | **결제와 원장만. 이체는 후순위.** 일정이 남으면 "내부 장부 이동"을 추가한다 |
| 원장 관점 | **상점(가맹점) 기준, 복식부기 용어 그대로 사용** (차변·대변, 자산·수익). 외부 PG가 돈을 보관하므로 돈 보관 제외 항목과 충돌하지 않는다. 회계 지식이 부족하다는 우려가 있었으나 용어를 그대로 쓰기로 선택했다. 필요한 개념은 4절 |
| 계정 목록 | **최소 2개: 카드사 미수금(자산) + 매출(수익).** 수수료·정산 계정은 범위 밖이고, 필요해지면 계정을 추가한다 |
| 분개 트리거 | **PG 동기 응답으로 분개하고, 웹훅·조회는 보정용.** 응답을 잃은 경우에만 웹훅·조회로 확정한 뒤 분개한다 |
| 정합성 검증 | **테스트 + 주기 검증 잡.** 모든 시나리오 테스트 끝에 불변식을 검사하고, 실행 중에는 주기적으로 PG 조회와 대조한다 |
| orderId 중복 | **`orderId`는 유니크.** 다른 멱등키로 같은 `orderId`의 결제 생성을 요청하면 거부한다 (코드 `DUPLICATED_ORDER_ID`, HTTP 400) |
| 금액 불일치 | **거부하고 결제 상태 유지 + 감사 로그.** `INVALID_REQUEST`(400)로 거부하고 결제는 `IN_PROGRESS`로 둔다 |
| 인증 단계 | **모의 PG의 테스트 전용 엔드포인트.** 어댑터는 승인·취소·조회만 가진다 |
| 트랜잭션 경계 | **3단계 분리.** PG 호출은 DB 트랜잭션 밖에서 하고, 요청 기록(tx1)과 결과 반영(tx2)을 각각 커밋한다 |
| 결과 불명 복구 | **같은 PG 멱등키로 최대 2회 재시도 → 한도 초과 시 `UNKNOWN` + PG 조회 잡으로 확정** |
| UNKNOWN 응답 | **500 `FAILED_PAYMENT_INTERNAL_SYSTEM_PROCESSING` + 같은 멱등키 재호출 안내.** 재호출하면 최신 결과를 돌려준다 |
| 동시성 제어 | **조건부 UPDATE.** 취소 금액 예약과 상태 전이를 `WHERE` 조건이 붙은 UPDATE 한 문장으로 처리한다. 비관적 락(`SELECT FOR UPDATE`)과 낙관적 락은 쓰지 않는다 |
| 테스트·부하 | 4-8절. **Testcontainers + 실제 PostgreSQL**, 부하는 **k6**, 서버 중단은 **장애 주입 훅(예외 발생)** |
| 웹훅 수신 | 4-7절. **모의 PG가 서명하고 우리가 검증**, **본문은 신호로만 쓰고 결제 조회로 확인**, **저장 후 즉시 200, 처리는 비동기** |
| 자체 멱등키 정책 | 4-6절. **필수**, **성공 + 결정적 오류만 재생**, **보관 15일** |
| 동시 취소 | **잔액 범위 안에서 동시 허용.** 같은 멱등키의 중복은 한 번만 처리하고, 다른 멱등키의 부분 취소는 예약액이 잔액 안이면 동시에 진행한다 |

- 이체를 후순위로 둔 것은 의도 문서의 "이체·원장 기록" 중 이체 부분의 시점을 미룬 결정이다. 의도 문서 자체는 수정하지 않았다. 정식으로 바꾸려면 의도 문서 개정이 필요하다.
- 원장에서 말하는 "계정"은 은행 계좌가 아니라 회계 항목이다. 외부 계좌나 실제 돈이 없어도 동작한다.

## 2. 역할과 경계

```
클라이언트(가상 상점 서버)
        │  결제 생성 / 승인 / 취소 / 조회  (Idempotency-Key)
        ▼
 우리 결제 서버 (Spring Boot, PostgreSQL)
   ├─ 결제 도메인 (상태 전이)
   ├─ 원장 (복식부기 분개)
   ├─ 멱등키 저장소 (DB)
   └─ PaymentGateway 어댑터 (인터페이스)
        │  Basic 인증, Idempotency-Key
        ▼
 모의 PG (토스 규격, 장애 주입)  ──웹훅──▶ 우리 서버
```

- 어댑터 인터페이스 뒤에 모의 PG를 두고, 실제 PG 샌드박스 어댑터로 교체할 수 있게 한다.
- 우리 서버는 PG에 보내는 요청에도 멱등키를 붙이고, 요청 전에 키와 요청 상태를 DB에 먼저 기록한다.

## 3. 결제 상태 (제안)

토스 상태를 그대로 따른다(`02`의 4절). 우리 서버는 PG 응답과 웹훅으로 상태를 갱신한다.
`READY → IN_PROGRESS → DONE → (PARTIAL_CANCELED →)* CANCELED`, 실패 `IN_PROGRESS → ABORTED`, 만료 `READY → EXPIRED`·`IN_PROGRESS → EXPIRED`(승인 만료 10분, `READY` 만료 시간은 설정값)

- 웹훅은 `DONE`, `ABORTED`, `EXPIRED`, `CANCELED`, `PARTIAL_CANCELED`로 전이될 때만 오고 `READY`, `IN_PROGRESS`에서는 오지 않는다(`02`의 4절).
- 부분 취소 이후의 전이(`PARTIAL_CANCELED → CANCELED`, 반복 부분 취소)는 토스 그림에 없고 우리의 가정이다.

- 전이 규칙은 한 곳(도메인)에 두고, 허용되지 않는 전이는 거부한다.
- 상태 역행 이벤트(늦게 도착한 웹훅 등)는 폐기한다.

## 4. 원장

### 4-0. 필요한 최소 개념

- **분개:** 한 건의 거래를 계정별 차변·대변으로 나눠 기록한 묶음
- **불변 조건:** 한 분개 안에서 차변 합계 = 대변 합계
- **자산 계정(카드사 미수금):** 늘면 차변, 줄면 대변
- **수익 계정(매출):** 늘면 대변, 줄면 차변
- **정정:** 기존 분개를 고치지 않고 반대 분개를 추가한다 (취소가 이에 해당)

### 4-1. 관점과 계정

1절에서 확정 (상점 기준, 카드사 미수금 + 매출)

### 4-2. 승인·취소 분개 규칙 (확정)

10,000원 결제 기준 예시입니다.

| 이벤트 | 분개 | 비고 |
|---|---|---|
| 승인 `DONE` | 차변 카드사 미수금 10,000 / 대변 매출 10,000 | PG가 승인을 확정했을 때만 남긴다 |
| 부분 취소 3,000 | 차변 매출 3,000 / 대변 카드사 미수금 3,000 | 취소 건마다 분개 1건 |
| 남은 금액 전체 취소 7,000 | 차변 매출 7,000 / 대변 카드사 미수금 7,000 | 전체 취소도 "남은 잔액만큼"의 역분개로 통일 |
| `ABORTED`, `EXPIRED` | 분개 없음 | 돈이 움직이지 않음 |
| `READY`, `IN_PROGRESS` | 분개 없음 | 승인 전이라 확정된 거래가 아님 |

**불변식**
1. 모든 분개는 차변 합계 = 대변 합계 (DB 제약으로도 막는다)
2. 한 결제의 카드사 미수금 순잔액 = PG가 응답한 `balanceAmount` (테스트와 주기 검증 잡으로 확인)
3. 취소 금액 합계 ≤ 승인 금액. 초과하면 `NOT_CANCELABLE_AMOUNT`(403)
4. 분개는 수정·삭제하지 않는다

**중복 분개 방지:** PG가 거래마다 다르게 주는 `transactionKey`(Payment의 `lastTransactionKey`, Cancel의 `transactionKey`)와 결제를 묶어 분개 테이블의 유니크 키로 쓴다. 같은 응답이나 웹훅이 두 번 처리되어도 분개는 한 번만 생긴다.

**응답 유실 시:** 승인·취소 응답을 받지 못했다면 상태가 불확실하므로 분개하지 않고, 같은 멱등키 재시도나 PG 조회로 확정한 뒤 남긴다. 복구 순서는 4-4에서 확정했다.

**범위 밖:** 수수료, 정산, 가상계좌 입금 처리

## 4-3. 결제 생성과 금액 위변조 검증 (확정)

```
1. 상점 서버 → 우리 서버   결제 생성 (orderId, amount, orderName)   → READY, 금액을 서버에 저장
2. (인증 스텁)             모의 PG의 테스트 전용 엔드포인트          → paymentKey 발급, IN_PROGRESS
3. 상점 서버 → 우리 서버   승인 (paymentKey, orderId, amount)
4. 우리 서버               요청 amount를 1단계 저장 금액과 대조 → 일치할 때만 PG confirm 호출
5. 모의 PG                 amount를 다시 대조한 뒤 승인
```

- 금액은 1단계에서 서버가 정해 저장하고, 3단계의 `amount`는 대조에만 쓴다. 이것이 금액 위변조 방어다.
- 방어선은 두 겹이다. 우리 서버가 먼저 거부하고, 모의 PG도 `INVALID_REQUEST`(400)로 다시 거부한다.
- 토스 핵심 API에는 결제 생성이 없다(결제창 SDK가 클라이언트에서 처리). 그래서 2단계 인증은 모의 PG에만 있는 테스트 전용 엔드포인트로 두고, 어댑터에는 넣지 않는다.
- 불일치 시 결제는 `IN_PROGRESS`로 유지해 올바른 금액으로 재승인할 수 있고, 불일치 시도는 감사 로그로 남긴다.
- 제약: `orderId` 6~64자(영문·숫자·`-`·`_`·`=`), `orderName` 최대 100자 (`02`의 2~3절)
- **`DUPLICATED_ORDER_ID`: HTTP 400 (확정).** 토스 에러 코드 문서의 상태를 따른다. 이 코드는 토스에서 승인·취소 표가 아니라 카드번호 결제·가상계좌 발급·자동결제 승인 쪽에 나오므로, 우리 결제 생성 API에 적용하는 것은 우리의 선택이다.

## 4-4. 외부 PG 호출과 트랜잭션 경계 (확정)

```
tx1 (커밋)  검증 → 요청 기록 생성 (PENDING, PG용 멱등키 고정)
            ── 트랜잭션 밖 ──
PG 호출     같은 PG 멱등키로 승인/취소 요청 (타임아웃 값은 설정, 초기 5초)
            ── 트랜잭션 밖 ──
tx2 (커밋)  결제 상태 갱신 + 분개 + 요청 기록 SUCCEEDED/FAILED + 클라이언트 멱등키 COMPLETED
```

- PG 호출 중에는 DB 트랜잭션과 락을 잡지 않는다. 외부 호출이 느리면 커넥션과 락이 묶이기 때문이다.
- tx2에서 상태, 분개, 멱등키 완료 기록을 한 트랜잭션으로 묶어 일부만 반영되는 상태를 막는다.
- 승인·취소 시도마다 요청 기록(`payment_request` 등) 한 행을 두고 상태는 `PENDING / SUCCEEDED / FAILED / UNKNOWN`으로 한다. 결제 상태는 토스 상태 그대로 둔다.
- PG용 멱등키는 tx1에서 정해 저장한다. 서버가 PG 호출 뒤 죽어도 재시작 후 같은 키로 재시도할 수 있다.
- 취소는 tx1에서 취소 금액을 예약해 동시 취소가 잔액을 넘지 않게 한다(방식은 4-5에서 확정).

| 상황 | 처리 |
|---|---|
| PG가 명시적 거절(예: 403 `REJECT_CARD_COMPANY`) | 요청 `FAILED`, 분개 없음 |
| 타임아웃·응답 유실 | 같은 PG 멱등키로 최대 2회 재시도(백오프). PG가 이미 처리했다면 첫 응답이 반환된다 |
| 재시도 한도 초과 | 요청 `UNKNOWN`. 상점에는 500 `FAILED_PAYMENT_INTERNAL_SYSTEM_PROCESSING`을 주고 같은 멱등키 재호출을 안내한다. 주기 잡이 PG 조회로 확정한다 |
| tx1 이후, PG 호출 전 서버 사망 | `PENDING`이 남음 → 복구 잡이 같은 키로 재시도 |
| PG 성공 후, tx2 전 서버 사망 | 같은 키로 재요청하면 PG가 첫 응답을 반환 → 정상 반영 |
| PG가 409 `IDEMPOTENT_REQUEST_PROCESSING` | 잠시 후 같은 키로 재요청 |

- 재시도 횟수(2회)와 타임아웃(5초)은 초기값이며 설정으로 둔다.
- 토스 문서는 에러 응답 뒤 키를 바꿔 재시도하는 것을 위험하다고 명시한다(`02`의 5절). 재시도는 항상 같은 PG 멱등키로 한다.

## 4-5. 동시성 제어 (확정)

| 경합 지점 | 막아야 할 결과 | 처리 |
|---|---|---|
| 동시 취소 | 잔액 초과 환불 | 취소 금액 예약 (아래) |
| 동시 승인 | PG 이중 승인 | 요청 기록 테이블의 부분 유니크 인덱스 (아래) |
| 동기 응답 vs 웹훅 | 상태 역행, 분개 중복 | 조건부 상태 전이 + 분개 유니크 키(4-2) |
| 같은 멱등키 동시 전송 | 이중 처리 | 멱등키 테이블(4-6에서 확정) |

**취소 금액 예약 (tx1)**
```sql
UPDATE payment
   SET reserved_cancel_amount = reserved_cancel_amount + :amt
 WHERE id = :id
   AND status IN ('DONE', 'PARTIAL_CANCELED')
   AND total_amount - cancelled_amount - reserved_cancel_amount >= :amt;
```
- 영향 행이 1이면 예약 성공, 0이면 거부한다. 거부 사유는 한 번 더 조회해 구분한다(결제 없음 `NOT_FOUND_PAYMENT`, 취소 불가 상태 `NOT_CANCELABLE_PAYMENT`, 잔액 초과 `NOT_CANCELABLE_AMOUNT`).
- 취소 성공(tx2) 시 예약액을 `cancelled_amount`로 옮기고, 명시적 실패(`FAILED`) 시 예약을 해제한다.
- **`UNKNOWN`이면 예약을 유지한다.** 결과가 불명인데 예약을 풀면 그 사이 다른 취소가 들어와 초과 환불이 될 수 있어서, 조회 잡이 확정할 때까지 묶는다.
- 전체 취소(금액 미지정)는 현재 잔액 전부를 예약한다. 두 번째 전체 취소는 예약 조건에서 실패해 `NOT_CANCELABLE_AMOUNT`로 거부된다.

**동시 승인 차단:** 요청 기록 테이블에 "같은 결제의 승인 요청 중 `PENDING / UNKNOWN / SUCCEEDED`는 하나만" 부분 유니크 인덱스를 둔다. 충돌하면 진행 중이면 `ALREADY_PROCESSING_REQUEST`(400), 이미 승인됐으면 `ALREADY_PROCESSED_PAYMENT`(400)로 거부한다.

**상태 전이:** `UPDATE ... SET status = :new WHERE id = :id AND status = :expected`로 전이하고, 영향 행이 0이면 역행·중복으로 보고 폐기한다.

**전제와 주의**
- 조건부 UPDATE도 PostgreSQL이 해당 행에 행 잠금을 건다. 개발자가 명시적으로 잠그지 않을 뿐이다. 먼저 온 UPDATE가 끝나면 기다리던 UPDATE가 `WHERE`를 새 값으로 다시 평가한다.
- 위 동작은 PostgreSQL 기본 격리 수준(READ COMMITTED)을 전제로 하며, 구현 후 동시성 테스트(4-8)로 검증한다.
- 같은 멱등키의 중복 취소는 한 번만 처리하고(4-6), 다른 멱등키의 부분 취소는 별개 요청으로 본다. 토스도 부분 취소를 여러 번 허용한다.

## 4-6. 우리 서버의 멱등키 정책 (확정)

모의 PG의 정책(`02`의 5절, 7-0절)을 재사용하고 아래 세 가지를 추가로 정했다.

| 항목 | 결정 |
|---|---|
| 키 필수 여부 | **필수.** 결제 생성·승인·취소(모든 POST)에서 `Idempotency-Key`가 없으면 400 `INVALID_REQUEST`로 거부한다. 토스는 선택이므로 우리 정책이 다르다. 토스에 전용 에러 코드는 없다 |
| 재생 범위 | **성공 + 결정적 오류만 재생.** 성공과 확정된 4xx(카드 거절 등)는 같은 키로 재요청하면 첫 응답을 그대로 돌려준다. 5xx, `UNKNOWN`, 타임아웃 같은 일시 오류는 재생하지 않고 같은 키로 재처리를 허용한다 |
| 보관 기간 | **15일.** `expires_at` 기준 정리 배치가 필요하다 |

재사용하는 항목
- 저장소: PostgreSQL 멱등키 테이블 (Redis 안 씀)
- 키 범위: 상점 API 키 + 경로 + HTTP 메서드 + 키 값. 길이는 최대 300자이고 초과하면 400 `INVALID_IDEMPOTENCY_KEY`
- 처리 중 재요청: 409 `IDEMPOTENT_REQUEST_PROCESSING`
- 같은 키 + 다른 본문: 422 `IDEMPOTENCY_KEY_REUSED`
- `IN_PROGRESS`가 남은 경우: 30초 후 재요청이 오면 상태를 확인해 확정하거나 재처리
- GET 요청의 키는 무시

4-4와의 연결
- 완료 기록(`COMPLETED`)은 tx2에서 상태 갱신·분개와 한 트랜잭션으로 남긴다.
- 결과가 `UNKNOWN`인 요청에 같은 키로 재호출이 오면 새 PG 요청을 만들지 않고, 기존 요청 기록과 그 PG 멱등키를 재사용해 복구를 이어 간다. 이 응답은 "일시 오류"라서 멱등키 테이블에는 재생용으로 저장하지 않는다.
- 재처리 시에도 PG용 멱등키는 요청 기록에 고정된 값을 쓴다.

## 4-7. 웹훅 수신 처리 (확정)

```
1. 서명 검증 실패 → 400 (저장하지 않음)
2. 이벤트 테이블(inbox)에 저장 (유니크: paymentKey + status + lastTransactionKey)
   - 이미 있으면 200으로 응답하고 종료 (중복은 오류가 아님)
3. 200 응답 (10초 안에)
4. 비동기 워커: PG에 결제 조회 → 조건부 상태 전이(4-5) → 필요 시 분개(4-2)
```

| 항목 | 결정 |
|---|---|
| 서명 | 모의 PG가 `{본문}:{전송시각}`을 HMAC-SHA256으로 서명해 헤더로 보내고, 우리가 검증한다. 토스 문서의 방식을 차용한 것이며 카드 결제 웹훅에 토스가 실제로 서명하는지는 미확인이다(`02` 6절 정정 참고). 보안 키는 모의 PG 설정값 |
| 본문 신뢰 | **신호로만 사용.** 본문의 상태는 믿지 않고 PG 조회 API의 현재 상태로 반영한다. 위조와 순서 뒤바뀜에 강하고 4-2의 "웹훅은 보정용" 원칙과 일치한다. 대신 조회 호출이 늘어난다 |
| 처리 방식 | **저장 후 즉시 200, 처리는 비동기.** 10초 안에 200을 보장하고 처리 실패 시 워커가 재시도한다 |
| 중복 | 유니크 키 충돌이면 200으로 응답한다. 오류로 응답하면 PG가 최대 7회 재전송한다 |
| 역행·지연 이벤트 | 조회한 현재 상태에서 조건부 UPDATE가 영향 행 0이면 폐기하고 200 처리한다 |
| 분개 | 4-2의 유니크 키(결제 + PG 거래 키)가 중복 분개를 막는다 |

- inbox 처리 상태는 `RECEIVED / PROCESSED / FAILED`로 두고, 워커는 `FAILED`를 재시도한다. 재시도 횟수와 간격은 구현 때 정한다.
- 조회가 필요하므로 어댑터의 조회 메서드(`02`의 2절)를 쓴다.

## 4-8. 테스트·부하 시나리오 (확정)

모든 시나리오는 끝에 공통 불변식을 검사한다: ① 분개별 차변 합 = 대변 합 ② 결제별 미수금 순잔액 = `balanceAmount` ③ 취소 합계 ≤ 승인 금액

**환경:** 동시성·장애 시나리오는 JUnit + Testcontainers의 실제 PostgreSQL에서 돌린다(조건부 UPDATE와 격리 수준 동작은 실제 DB에서만 검증된다). 부하 테스트는 k6. 서버 중단은 tx1 뒤와 tx2 앞에 둔 테스트 전용 장애 주입 훅(예외 발생)으로 재현한다. 실제 프로세스 강제 종료와는 다르다는 점을 결과 문서에 밝힌다.

**동시성**
| # | 시나리오 | 기대 결과 |
|---|---|---|
| S1 | 잔액 7,000원에 5,000원 부분 취소를 N건 동시 요청 (서로 다른 멱등키) | 1건만 성공, 나머지 `NOT_CANCELABLE_AMOUNT`(403) |
| S2 | 같은 결제에 전체 취소를 N건 동시 요청 | 1건만 성공 |
| S3 | 같은 멱등키로 승인을 N건 동시 전송 | 승인 1회, 나머지는 첫 응답 재생 또는 409 |
| S4 | 같은 결제에 다른 멱등키로 승인 N건 동시 | PG 호출 1회, 나머지는 `ALREADY_PROCESSING_REQUEST`·`ALREADY_PROCESSED_PAYMENT`(400) |

**중복·위변조**
| # | 시나리오 | 기대 결과 |
|---|---|---|
| S5 | 같은 멱등키 + 다른 본문 | 422 `IDEMPOTENCY_KEY_REUSED` |
| S6 | 다른 멱등키로 같은 `orderId` 결제 생성 | 400 `DUPLICATED_ORDER_ID` |
| S7 | 승인 `amount` 위변조 | 400 `INVALID_REQUEST`, 결제는 `IN_PROGRESS` 유지, 감사 로그 |

**중간 실패 (모의 PG 장애 주입, 서버 중단)**
| # | 시나리오 | 기대 결과 |
|---|---|---|
| S8 | PG는 승인했지만 응답이 유실됨 | 같은 PG 멱등키 재시도로 첫 응답 수신, 승인·분개 각 1건 |
| S9 | PG 타임아웃이 재시도 한도를 초과 | 요청 `UNKNOWN`, 취소 예약 유지, 조회 잡이 확정 |
| S10 | tx1 커밋 후 PG 호출 전 중단 | 복구 잡이 같은 키로 재시도 |
| S11 | PG 성공 후 tx2 전 중단 | 같은 키 재요청으로 정상 반영, 분개 1건 |
| S12 | 중복 웹훅, 순서가 뒤바뀐 웹훅 | 분개 중복 없음, 상태 역행 없음 |

**부하 (완료 기준: 동시 결제를 부하 테스트로 재현)**
| # | 시나리오 | 확인할 것 |
|---|---|---|
| L1 | 서로 다른 결제를 대량 동시 승인 | 처리량, 응답 시간, 오류율, 종료 후 불변식 |
| L2 | 같은 결제에 취소가 몰리는 경합 | 초과 환불 0건, 성공 건수 = 잔액으로 가능한 건수 |
| L3 | L1에 장애 주입(타임아웃·응답 유실)을 섞음 | 불변식 유지, `UNKNOWN`이 복구 잡으로 수렴 |

- 동시 요청 수와 목표 처리량 같은 수치는 구현 후 측정해 정하고, spec에서는 정하지 않는다.
- 결과는 GitHub 공개용으로 시나리오별 통과 여부와 부하 테스트 리포트(k6 요약)를 문서로 남긴다.
